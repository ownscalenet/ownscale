# Agent notes

Conventions for AI coding agents (and contributors) working in this repo.

## Error handling

Always use `defer derrors.Wrap(&err, "f(args)", ...)` for exported
functions that return an `error`, instead of manually wrapping errors with
`fmt.Errorf("context: %w", err)` at each call site.

`derrors.Wrap` (`derrors/derrors.go`) is a small helper
modeled on
[golang/pkgsite's `derrors.Wrap`](https://github.com/golang/pkgsite/blob/master/internal/index/index.go#L35):

```go
func Wrap(errp *error, format string, args ...any) {
	if *errp != nil {
		*errp = fmt.Errorf("%s: %w", fmt.Sprintf(format, args...), *errp)
	}
}
```

Usage pattern — give the function a named `err` return and defer the wrap
at the top:

```go
func (c *Ctl) MethodName(ctx context.Context, subdomain string) (_ string, err error) {
	defer derrors.Wrap(&err, "c.MethodName(%q, %q)", subdomain)
	...

func PkgFunc(ctx context.Context, subdomain string) (_ string, err error) {
	defer derrors.Wrap(&err, "PkgFunc(%q, %q)", subdomain)
    ---
}
```
Do not put the whole type in the string argument of `derrors.Wrap`:

```go
package service
func (c *Ctl) MethodName(ctx context.Context, subdomain string) (_ string, err error) {
    // good
	defer derrors.Wrap(&err, "c.MethodName(%q, %q)", subdomain)
    // bad
	defer derrors.Wrap(&err, "(*service.Ctl).MethodName(%q, %q)", subdomain)
```

## Other conventions

- **Doc comments**: every exported type/func/const has a doc comment
  starting with its own name, per standard Go convention (e.g. `// Wrap adds
  context...`, `// Ctl struct...`). Keep this up when adding exported
  identifiers.
- **Generated code**: `db/sqlcgen` is generated by
  [sqlc](https://sqlc.dev) — never hand-edit it. To change a query, edit
  `db/queries/*.sql` and run `sqlc generate`.
- **Migrations**: run via [goose](https://github.com/pressly/goose)
  (`db/db.go`'s `Migrate`).
- **Build/verify commands**: `go build ./...`, `go vet ./...`, and
  `go test ./...` (or `make build` / `make test`) all pass cleanly on
  `main` — run these after making backend changes.
- make sure variables and functions are not exported when not needed
- don't write excessively long comments. Just say why some code is the way it is
  and don't mention older/removed approaches/designs of the code.
- use table-driven tests whenever it fits, for example several tests for the same
  function, but with different inputs and expected outputs

## Testing

Try to create as few as possible fakes/mocks when testing the code. For example,
code that relies on dockerctl.Ctl are running with a real implementation of Ctl,
not a fake. The fake is done at the outside edge with docker's client.Client.
For tests that rely on a database, use a temporary sqlite which had the migrations
applied. When testing, try not to assert that some expected functions have been
called a number of times with specific arguments. Instead assert the results and
side-effects (but avoid code that relies on side-effects.)
